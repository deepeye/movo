# MOVO 合同预审智能体：产品与实施规格

更新：2026-09-23

## 1. 产品定义

对外名称使用“合同预审智能体”。内部继续使用现有工作流 Skill、写作规范、知识检索和 Word 导出能力实现，不增加新的智能体实体。

第一版只支持：**中国大陆企业的采购或服务合同，站在甲方/采购方立场，依据企业已经确认的合同审核规则进行预审**。

第一版不提供通用法律咨询，不自动签署、发送或修改原合同，不把公网搜索结果当作企业审核依据。输出是法务初审材料，最终结论由企业法务确认。

## 2. 目标用户和任务

主要用户是企业法务。业务人员上传一份待审合同后，系统应完成：

1. 确认合同类型、我方身份和本次关注点；
2. 载入当前生效的企业审核规则；
3. 解析合同并提取关键条款；
4. 按规则逐项判定，保留合同原文和规则原文依据；
5. 给出风险等级、原因、修改建议和待确认事项；
6. 生成可下载的 Word 预审报告；
7. 记录实际读取的规则文档 ID、名称和文件摘要，便于复核和追溯。

## 3. 第一版规则来源

法务把审核规则写成一份有编号的知识文档，并在工作流 Skill 中指定它。运行时读取该文档的已解析内容，记录文档 ID 和文件摘要。规则文档较长时，Agent 应能继续按章节读取，不能把一次检索得到的片段当作全部规则。

规则清单的人工确认和不可变版本发布可作为后续能力。第一版先用一份人工确认过的规则文档和测试合同验证审查效果。

## 4. 企业审核规则的数据结构

规则文档建议至少包含以下字段：

| 字段 | 含义 | 示例 |
| --- | --- | --- |
| rule_id | 稳定编号 | PAY-001 |
| category | 风险分类 | 付款与发票 |
| title | 规则名称 | 禁止100%预付款 |
| applicable_when | 适用条件 | 我方为采购方 |
| requirement | 审核要求 | 预付款原则上不超过合同金额30% |
| severity | 默认风险等级 | high |
| pass_condition | 通过条件 | 预付款比例小于等于30% |
| fail_condition | 命中条件 | 预付款比例大于30% |
| exception | 例外条件 | 经财务负责人书面批准 |
| suggestion_template | 建议文本 | 调整为验收后分期付款 |
| source_location | 原文位置 | 第3章第2条 |

判定状态固定为：`pass`、`risk`、`missing`、`not_applicable`、`needs_human_review`。没有找到条款时使用 `missing`，不能自动视为通过。

## 5. 第一版工作流

### 节点1：读取待审合同

- 类型：`read_material`
- 输入：用户上传的 PDF 或 DOCX 合同
- 输出：解析后的正文、表格、文件名和解析质量
- 失败规则：扫描件无法可靠识别、正文为空或文件加密时停止审查并说明原因

### 节点2：识别任务上下文

- 类型：`extract_info`
- 输出：合同类型、我方身份、对方身份、交易背景、用户关注点
- 若合同类型或我方身份无法确定，先向用户确认，不继续生成结论

### 节点3：载入审核规则

- 类型：`read_material` 的“指定知识文档”来源（待实现）
- 第一版按 Skill 绑定的文档 ID 读取，不以 `knowledge.search@v1` 的相似度片段代替规则全文
- 输出：文档 ID、规则原文、可用的位置线索；Agent 再提取规则 ID、要求、等级和适用条件
- 若没有可用规则，停止并提示配置规则，不能退化为无依据的通用法律判断

### 节点4：结构化合同

- 类型：`extract_info`
- 至少提取：主体、标的、金额、税费、付款、发票、交付、验收、质保、知识产权、保密、数据、违约、赔偿、解除、不可抗力、争议解决、生效和附件
- 每个字段保留合同原文及位置；未找到时标记缺失

### 节点5：逐规则判定

- 类型：`review_check`（Agent preset 指导节点，前端已提供）
- 对每一条适用规则输出判定状态、风险等级、规则依据、合同依据和判断理由
- 一条风险必须同时具有 `rule_id` 和合同原文证据；缺少任一项时降级为 `needs_human_review`
- 第一版禁止使用公网搜索补充判断

### 节点6：交叉检查

- 类型：`review_check`（待验证 Agent 能按指令完成）
- 检查金额大小写、日期、主体名称、付款与验收、违约责任与责任上限、正文与附件之间的冲突
- 该节点输出“文本内部冲突”，不声称违反企业规则或法律

### 节点7：生成审核建议

- 类型：`generate_content`
- 绑定“合同预审报告写作规范”
- 每项风险包含：风险等级、问题、合同原文、规则依据、影响、建议替换文本、退让方案、待法务确认事项
- 不得编造合同条款、规则编号、法律条文或审批事实

### 节点8：结果自检

- 类型：`review_check`（待验证 Agent 能按指令完成）
- 检查所有风险是否有双重证据，风险等级是否来自规则，金额与主体是否和原合同一致，报告是否把缺失条款误写成现有条款
- 发现未通过项时要求 Agent 修正报告；无法可靠修正则显著标记“需要人工复核”。当前节点属于执行指导，自动重试次数尚未由运行时强制保证

### 节点9：导出 Word

- 类型：`export_delivery`
- 文件名：`合同预审报告_合同名称_YYYYMMDD.docx`
- 同时在会话中展示摘要，Word 是正式交付物

## 6. Word 报告结构

1. 封面：合同名称、送审人、审查时间、规则版本
2. 审查范围和限制
3. 合同基本信息
4. 风险摘要：高、中、低、待确认数量
5. 高风险事项
6. 完整规则核对表
7. 缺失条款和信息
8. 合同内部冲突
9. 修改建议及可替换文本
10. 谈判退让方案
11. 待业务或法务确认事项
12. 依据索引：合同位置、规则 ID、规则原文位置

风险表固定列为：序号、风险等级、问题分类、合同原文、规则依据、判断、修改建议、替换文本、处理状态。

## 7. MOVO 当前可直接复用的能力

- `read_material` 已映射到 `document.parse@v1`，支持 PDF、DOCX 等材料解析；
- `internal_search` 已映射到 `knowledge.search@v1`，能返回知识片段和页码引用；
- `extract_info` 和 `review_check` 已有 Agent preset 映射，但不是独立可调用 Tool；工作流编辑器现已提供通用“校验复核”节点；`generate_content` 和 `export_delivery` 有实际 Tool 能力；
- Word 渲染已经支持 Markdown 到 DOCX、模板、封面和目录；
- execution-v3 已有 Skill、Tool、Evidence 和 Artifact 展示。

## 8. 为这个场景需要补的最小平台能力

### P0：让 Skill 能引用并读取指定知识文档

现有 `knowledge.search@v1` 是 RAG 检索，`document.parse@v1` 只接受用户所有的附件。先在 `read_material` 中配置指定知识来源，再增加受服务端授权的按文档读取能力。不要把知识库原文件路径直接交给现有附件 Tool。

### P0：明确审查协议并验证覆盖率

使用现有 `extract_info`、`generate_content` 和 Agent 指令先实现规则提取、逐条判定、证据核对。每条规则必须有状态，缺失证据时标记人工复核。先用测试合同验证 Agent 是否稳定覆盖全部规则，再决定是否需要新增独立复核 Tool。

### 已实现：在编辑器暴露通用复核节点

`review_check → dsh.review_check@v1` 会编译为 Agent 的复核指导。节点可配置检查对象、判定依据、证据要求和失败处理；它本身不能保证结构化判定或自动重试。若测试显示多场景都需要确定性审查，再设计独立 Tool。

### P1：规则集结构化与人工确认

在第一版验证后，再考虑“上传规则文档 → 自动提取 → 表格校对 → 发布规则版本”。当前代码没有这条发布链路，不能把它当作 P0 的现成依赖。

### P0：证据双链

风险项同时引用：

- 待审合同中的原文和位置；
- 企业规则中的规则 ID、原文和位置。

现有知识证据已有页码字段；需要确认上传合同解析后的证据坐标能稳定到页码、标题路径或段落编号。坐标不可靠时报告使用原文摘录并标记“位置待确认”。

### P1：专用报告模板

增加合同预审 Word 模板和风险表样式。暂不修改原合同，也不生成带修订痕迹的合同版本。

## 9. 首批验收数据集

第一批准备 20 份脱敏或虚构合同：

- 8份采购合同；
- 8份服务合同；
- 2份扫描质量较差的合同；
- 2份超出支持范围的合同，用于验证拒绝和转人工。

每份合同由人工标注：合同类型、我方身份、适用规则、预期高/中风险、缺失条款、原文位置和允许存在分歧的项目。

核心指标：

| 指标 | 第一版目标 |
| --- | --- |
| 规则覆盖率 | 100%适用规则都有判定状态 |
| 高风险召回率 | 不低于90% |
| 证据完整率 | 100%风险项有合同证据和规则依据 |
| 幻觉率 | 不得出现虚构的合同条款或规则编号 |
| Word交付成功率 | 20份全部生成并可打开 |
| 重复运行稳定性 | 同一合同5次运行，高风险清单基本一致 |

## 10. 演示视频脚本

使用一份虚构的供应商服务合同和一份公开的企业审核规则：

1. 展示规则集中三条明确规则，例如预付款比例、验收标准和责任上限；
2. 上传合同，说明“我方为甲方，按公司规则预审”；
3. 展示 Agent 自动载入规则版本、解析合同和逐项核对；
4. 打开一项高风险，分别查看合同原文与企业规则依据；
5. 展示建议替换文本和退让方案；
6. 导出 Word，并现场核对报告中的金额、原文和规则编号；
7. 明示这是企业规则驱动的预审，最终由法务确认。

## 11. 可借鉴的 WorkBuddy 方法

WorkBuddy 官方将“专家”描述为人设、方法论和工具链的组合，将 Skill 描述为可执行脚本和工作流；Buddy 应用再提供场景入口。MOVO 可以借鉴这种对外包装，但不需要复制其 Agent 实体。

公开的 WorkBuddy 合同审查案例强调：先明确合同类型、我方角色和关注点，再建立审查清单，进行风险审查、标准范本比对，输出修改话术和谈判备选。MOVO 第一版采纳其中的角色确认、清单驱动、风险分级、替换文本和谈判备选；标准范本比对、版本差异和直接修改原合同放到后续版本。

## 12. 后续版本边界

### V1.1

- 标准范本与送审合同逐条比对；
- 两个合同版本的差异审查；
- 用户在报告中确认、驳回或调整风险等级；
- 人工反馈沉淀为规则建议，但不能自动修改生效规则。

### V1.2

- 在原 DOCX 中生成批注或修订痕迹；
- 支持乙方视角；
- 增加销售、保密协议等合同类型；
- 与合同管理或审批系统通过 MCP 对接。

每扩展一种合同类型或我方角色，都必须增加独立规则集和验收合同，不能只修改提示词后直接宣称支持。

## 13. 基于当前代码的升级方案

### 13.1 已验证的代码事实

- `read_material` 对应 `document.parse@v1`；该 Tool 当前强制提供 `artifacts`，并按用户上传附件的所有权前缀校验路径。
- `internal_search` 对应 `knowledge.search@v1`，实际执行 RAG 问答。个人知识的 `/personal-knowledge/{id}/ask` 能指定**个人资源 ID**；没有证据表明直接把组织文档 ID 传给这个参数就能精确读取该文档。
- 知识文档解析后已有 `knowledge_documents` 记录、`parsed_markdown_key`，以及按 `document_id + chunk_stage + ordinal` 保存的 raw/rag 片段。chat-api 已有按文档 ID 查看来源和单个 rag 片段的接口；没有供 Agent 顺序读取整份规则文档的 Tool。
- `extract_info`、`review_check` 仅映射为 Agent preset。`review_check` 已在用户端和管理端节点目录中开放；映射本身不会执行确定性逐条审查，也不会保证输出结构。
- `outputAlias` 会校验唯一，但 `compile_workflow_body` 没有显式渲染该字段。它不是运行时结果引用。组织 Skill 适配器只有在缺少显式节点描述时才可能把它写进描述。
- Tool Result 进入当前 Agent 上下文，并作为 Action Receipt 保存，但 Receipt 会压缩至 64 KiB。Execution Evidence 每轮仅保留最近 12 个 bundle，规范化时证据正文还有长度限制。不能声称它们能无损传递全文或完整规则清单。
- `content.produce@v1` 能读取同一轮的 Evidence；`artifact.export@v1` 可导出 Word。它们无需为此场景重做。

### 13.2 应先实现的最小闭环

1. 在 `read_material` 配置中加入来源选择：用户上传附件或指定知识文档。第一版绑定一份组织知识文档；个人 Skill 需要时再接个人资源选择器。保存的字段只包含来源类型和 ID，不引入 `inputAliases`、`outputSemanticType` 或独立规则版本。
2. 后端增加一个小的知识文档读取服务，按租户、用户、文档 ID 校验可见性、删除状态和解析状态。个人资源沿 `PersonalKnowledgeAccessService.require_view` 找到 `active_document_id`；组织文档沿 `get_product_extension().knowledge_access_policy.require_view` 的现有边界检查。社区版的组织知识权限模型与企业版扩展需分别验收。
3. 增加 `knowledge.read_document@v1` Tool，复用现有 `knowledge_document_chunks` 的 raw 片段或已保存的 Markdown。限定单次返回大小，并提供按顺序继续读取的能力；返回文档 ID、片段顺序、页码或标题路径、原文引用信息及是否读完。知识库的存储键不能伪装成用户上传的 `artifacts`。
4. 让 `read_material` 在 Skill 配置为知识来源时编译到新 Tool，上传来源继续编译到 `document.parse@v1`；这需要扩展当前仅按节点类型查找的 `workflow_capability` 映射。编译器还需明确渲染文档 ID、`outputAlias` 和“逐条列出规则并核对合同”的审查协议。每次 Tool 读取仍须由服务端授权；仅靠 Skill 文本不能授权访问。
5. 先用现有 Agent 推理完成规则提取和逐条判断，使用现有 Word 导出。报告记录所用规则文档 ID、文件摘要，以及无法定位的引用。用人工标注合同检查规则覆盖率、证据和重复运行一致性。

具体实现应把文档授权和分页读取放入独立小模块；`runtime/adapters.py` 只负责调用。现有 `runtime_parse_service.parse_documents` 继续处理上传附件，不承担知识文档读取。

### 13.3 先不纳入首版的方案

- `resource_scope_ref`：需要 Profile 与 Skill 绑定的服务端解析链路。现有代码未提供，首版可直接用文档 ID 加每次访问授权；如需严格限制“只能读 Skill 绑定的那份”，再设计不可伪造的绑定。
- `inputAliases`、`outputSemanticType`、Semantic Result Store：当前没有消费它们的执行器；先把 `outputAlias` 真正编入 Skill 指令，并以测试确认模型能正确传递结果。
- 独立的 `review.evaluate@v1` Tool 和自动重试：现有复核节点只提供 Agent 指导，准确率和跨场景复用仍需验证。
- 规则抽取、人工确认、不可变版本发布：这是独立的规则治理产品流程，不能作为本次演示闭环的前置条件。

### 13.4 验收顺序

先验证一个短规则文档能被完整读取、三条规则均被审查、两个证据来源能在报告中核对、Word 能打开。随后测试长规则文档的分页读取、用户撤权、文档替换、解析失败和超长合同；最后再扩大到 20 份标注合同。长文档若因 Tool Result 或 Evidence 压缩丢失关键内容，再增加可按 ID 取回的执行级结果存储。

## 14. 首轮手工测试配置

1. 在组织知识上传并完成解析一份短规则文档。建议先写三条有编号的规则，分别涉及预付款、验收和违约责任，记下规则编号与原文。确认测试用户有“内部知识”岗位能力，并能查看这份组织文档。
2. 在组织工作流 Skill 中配置两个“读取材料”节点：第一个选“用户上传材料”，第二个选“指定知识文档”，选择刚上传的文档。两个节点的输出名分别设为“待审合同”和“审核规则”。个人 Skill 可以选择自己的或已共享给自己的知识文档。
3. 加两个“抽取信息”节点：一个要求完整列出规则编号、适用条件、风险等级及原文位置；一个要求从合同抽取主体、金额、付款、交付、验收、违约和争议解决条款，缺失项明确标记。
4. 加“校验复核”节点：“审核什么”选择上游“待审合同”，“拿什么审核”选“选择已有依据”并选择上游“审核规则”；也可选“直接输入规则”填写短规则。节点要求写明按**全部适用规则**逐条输出 `pass`、`risk`、`missing`、`not_applicable` 或 `needs_human_review`。再加“生成内容”节点并绑定写作规范，要求每项给出规则原文与合同原文，报告首页写明 Tool 返回的规则文档 ID、名称和 checksum。最后加“导出交付”节点，要求 Word 格式。
5. 上传一份测试合同，要求“按公司审核规则预审这份合同并导出 Word”。检查规则是否全部列出、两类引用是否准确、文档 ID 与摘要是否记录、Word 是否可打开。

首轮请使用短规则文档。新 Tool 每次最多返回 5000 字，并提供 `next_cursor` 续读。较长文档虽然可以分页读取，但跨多次工具调用的规则覆盖率仍需实测；当前 Evidence 只保留同一轮最近 12 个 bundle。
