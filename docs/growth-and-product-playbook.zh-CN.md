# MOVO 30 天推广与产品实操手册

更新：2026-09-23。适用阶段：社区版发布约三周、已有初步流量和少量商业咨询，但缺少部署与持续使用数据。

## 1. 决策原则

本月的目标是找到一个能被陌生用户独立完成、愿意再次使用的企业任务。主指标是「不同组织完成首个真实任务的数量」，辅以次周再次使用、可复现的失败原因和进入付费试点的组织数。Star、克隆和群人数只作为发现渠道信号。

产品叙事聚焦一个任务闭环：**输入企业材料或目标 → Agent 规划与执行 → 展示证据和风险确认 → 交付可检查的文件或结果 → 团队复用**。暂不把功能数量或“支持最新 DSH”当作主要卖点。

### DSH 版本差异的产品含义

- `0.1.6-alpha.2` 增加插件管理、文件改动审阅、Office 预览，也调整 Session 多实例及插件加载行为。[发布说明](https://github.com/deepseek-ai/deepseek-harness/releases/tag/dsh-v0.1.6-alpha.2)
- `0.1.7-alpha.1` 改为 Session V4 日志、插件组合包声明 Agent 预设、工作区 `readBytes`；增加后台任务展示、会话反馈、文件交付与预览体验，并包含取消、重连、长工具参数等修复。[发布说明](https://github.com/deepseek-ai/deepseek-harness/releases/tag/dsh-v0.1.7-alpha.1)
- `0.1.7-alpha.2` 修复连续后台命令或一次性子代理结束后 Agent 停住、Web 重连后不显示回复等问题；工具结果截断策略改用 `maxInlineTokens`。[发布说明](https://github.com/deepseek-ai/deepseek-harness/releases/tag/dsh-v0.1.7-alpha.2)

上述多数是 DSH 自身客户端体验。MOVO 的 Web 和 Desktop 是独立界面，只有经过 Runtime Host 适配、端到端验证并实际暴露给用户的能力才能对外宣称。`0.1.7-alpha.2` 仍是预发布版。

## 3. 本月功能开发清单，按顺序执行

### P0-A：DSH 候选版本准入（第 1 周，技术前置）

**做什么**：在隔离环境评估 `0.1.7-alpha.2`，先记录相对 `0.1.6-alpha.1` 的 API、插件、能力和会话持久化差异。使用已有 `services/chat-api/scripts/evaluate_dsh_candidate.py` 与 `.github/workflows/dsh-upgrade-candidate.yml`。修复只放在 `dsh/runtime-host/` 下的小适配器，不在业务服务中增加上游专属逻辑。

**必须验证**：旧会话恢复后继续执行；Code 预设及工具仍在；Skill 可加载；子代理可返回；取消后立即发起下一轮；后台任务完成后能唤醒 Agent；MCP 图片和大工具结果可用；已有模型连接可用；完整镜像启动、备份与回滚。特别检查 Session V4、预设插件组合包、`readBytes`、Messages API 和 `maxInlineTokens` 变化。现有准入规则见 `services/chat-api/dsh/COMPATIBILITY.md`。

**完成定义**：候选评估通过，加上应用级回归及打包镜像 smoke test，再发布固定版本。任何一项失败时维持当前 DSH 版本，产品功能开发继续推进。

### P0-B：首任务引导和故障诊断（第 1–2 周，社区版）

**做什么**：在初始化完成后提供一个可选的、使用公开样例数据的首任务入口，例如“上传 3 份制度资料，回答问题并生成带引用的摘要”。显示模型、Embedding、检索和文件生成准备状态；失败时给出可复制的诊断包和明确的下一步操作。不要收集用户文档内容或密钥。

**完成定义**：新用户从空部署到导出第一份结果能自行完成；能区分镜像拉取、模型连通、知识解析、任务执行和文件交付五类失败。记录匿名、可关闭的阶段性统计或通过志愿者陪同部署人工记录。

### P1-A：Skill 验证台（第 2–3 周，社区版）

**做什么**：在现有工作流 Skill、写作规范、普通 Skill 和专家包之上增加可保存的验收用例。每条用例包含用户请求、样例附件、预期命中或禁止命中的 Skill、必须经过的能力节点、预期产物、引用要求和人工检查项。支持对草稿版与已发布版批量运行并比较结果。

现有“逻辑完整性检查”继续负责检查描述和节点是否说清楚；验证台负责真实执行后的业务结果。两者不能混为一个功能。

**完成定义**：一个 Skill 至少能保存 10 个正例、5 个反例和 5 个边界例；修改 Skill、模型、工具或 DSH 后可重复运行；能定位失败发生在选择、权限、节点执行、工具、生成或交付阶段。首版只提示风险，不强制阻断发布。

### P1-B：Skill 运行分析（第 3–4 周，社区版）

**做什么**：在每次执行中持久化 `skill_id`、`skill_version`、选择方式、节点类型、节点结果、耗时、Token、工具及产物摘要；管理端按 Skill 和版本显示运行次数、独立用户、完成率、人工接管率、失败节点、平均耗时与成本。允许从失败记录一键转成回归用例。

现有 Token 统计以请求、模型、用户和部门为中心；日志中的 Skill 名称不足以支持版本比较，因此这不是给当前报表加一张卡片，而是补齐 Skill 运行事实模型。

**完成定义**：团队能回答“哪个 Skill 真正在用、哪个版本变差、失败最多的节点是什么、一次成功交付花多少钱”，并能从同一页面进入对应会话和回归用例。

### P2：企业版只做有付费信号的试点

优先候选为按用户/角色分配模型与资源权限、SSO、审计保留、集中运维和合同支持。模型权限已有 [#76](https://github.com/himovo/movo/issues/76) 的明确请求，可先访谈报告者和两条商业咨询，确认实际组织规模、权限规则和购买决策。至少两家独立组织愿意进入设计伙伴试点，再投入完整企业版实施；没有验证前先做可演示原型和报价范围。

**本月暂缓**：同时支持多个 Agent Runtime、完整可视化工作流、泛化浏览器录制训练平台、语音、全面复刻 DSH 新 UI。浏览器和 Code Agent 目前依赖另行分发的专有 Desktop，对外内容应清楚标注演示环境及社区版可用范围。

## 4. 渠道分工

| 渠道 | 内容 | 发布节奏 | 唯一行动指引 |
| --- | --- | --- | --- |
| 自己的视频号 | 90–180 秒真实任务演示：原始材料、操作过程、失败/审批、最终文件；每周 1 条，长视频可拆成 3 个片段 | 每周 1 个任务场景 | 进入该场景的复现页 |
| 自己的公众号/官网 | 步骤、样例数据、版本、配置、常见失败和结果截图；每个视频对应 1 篇 | 每周 1 篇 | 下载样例并完成任务 |
| 外部公众号 | 独立测评，允许指出安装成本、效果边界及竞品差异；给统一测试任务和公开样例，不要求正面结论 | 先找 2 家试评，再扩大 | 指向同一复现页，使用独立渠道参数 |
| GitHub / DSH 社区 | 版本兼容说明、issue 修复、任务包案例、可复现技术文档 | 每个实质更新发布 | 试跑任务并反馈 issue/discussion |

外部作者最好是实际动手的技术作者。交付一个“测评包”：固定 MOVO 版本、最低机器配置、样例资料、三个测试任务、预期结果、已知限制、反馈入口。邀请他们同时记录安装耗时、首任务成功与否、生成文件是否可用。若有付费合作，应明示合作关系；不要把宣传稿包装成独立测评。

### 视频号第一条脚本

1. 前 10 秒：展示原始资料和目标，例如“用三份制度文件回答报销问题，并生成一页汇总”。
2. 10–40 秒：上传资料，展示模型与知识准备状态。
3. 40–100 秒：输入目标，展示计划、检索证据、工具调用及必要确认。
4. 100–140 秒：打开最终文件，逐项核对引用与结论；如有失败，展示重试或人工接管。
5. 最后 10 秒：给出版本、样例数据与复现页地址。

### 外部测评任务书

请作者独立完成三项：①从空机器部署并记录耗时；②用公开材料完成知识问答和文件交付；③尝试一个复杂边界，如长任务中断恢复或 MCP 接入。文章至少包含实际环境、成功项、失败项、与 DSH 的关系、适用对象和不适用情形。只提供可核查材料，不预写评价结论。

每个组织只统计一次，区分开发者本机、个人爱好者和企业团队。手工 CRM 或简表即可，先不建立复杂埋点系统。

| 指标 | 口径 | 采集方式 |
| --- | --- | --- |
| 有效访问 | 到达具体场景复现页的独立人次 | 渠道参数和网站分析 |
| 成功启动 | 首次进入初始化且服务健康的不同组织 | 自愿反馈或匿名、可关闭的事件 |
| 首任务完成 | 导出可检查结果且用户确认有用的不同组织 | 任务回执和回访 |
| 次周复用 | 7–14 天内第二次完成任务的不同组织 | 受访者回访或自愿事件 |
| 商业机会 | 有明确组织、场景、部署要求和采购负责人 | 一对一访谈记录 |

以下门槛是本月的**决策假设，不是行业基准**：若 10 位真实试用者中不足 5 位能自行完成首任务，优先修安装和引导；若完成者不足 3 位愿意次周再用，优先修结果质量和任务适配；若至少 2 家组织愿为同一治理需求进入付费试点，才将其提升为企业版 P0。每周按事实修订门槛。

## 9. 基于现有代码的产品迭代路线

### 9.1 先承认现有 Skill 已经是什么

MOVO 的 Skill 不是一段简单提示词，也不是待补齐的“轻工作流”。当前代码已经提供：

- 写作规范、普通 Skill、工作流 Skill 和专家包；
- 工作流节点配置、节点类型切换、节点生成/补全、逻辑检查和浏览器录制；
- 内容生成节点绑定写作规范，外部 Tool/MCP 节点和脚本插件；
- 外部 Skill ZIP 和专家包安装；
- 草稿、发布版本、分享、安装、更新、个人/组织范围及冲突处理；
- Runtime Profile 按用户权限动态编译模型、工具、Skill 和写作规范；
- DSH Agent Loop 根据目标自适应执行，可跳过、重复或并行节点，同时不能越过权限边界。

所以接下来不再投入“更多节点”“另一套低代码画布”“任务包对象”或“智能体中心”。这些方向会覆盖现有能力或复制现有发布体系。

### 9.2 产品模型：一个通用 Agent + Skill 能力系统

```text
用户目标
   ↓
MOVO 通用 Agent
   ├── 用户有权使用的模型与知识
   ├── 已安装或组织授权的 Skill
   ├── 用户有权使用的 Tool / MCP
   └── MOVO 的审批、审计、恢复与交付
```

“合同审核助手”“销售周报助手”可以作为快捷入口或场景名称，底层仍指向 Skill。现阶段不新增智能体实体，不再复制模型绑定、工具绑定、权限、版本和发布渠道。

### 9.3 第一优先级：Skill 验证台

现在能创建复杂 Skill，但无法把真实业务验收保存为可重复执行的资产。新增：

1. **用例库**：请求、附件、运行身份、期望命中/禁止命中的 Skill、人工检查项。
2. **结构断言**：必须/禁止出现的节点类型、工具、知识引用、审批和产物格式。
3. **结果检查**：关键词、引用数量、表格列、文件类型、JSON Schema，以及人工评分。
4. **版本对比**：同一组用例运行草稿版和已发布版，对比完成率、耗时、成本和产物。
5. **失败归因**：选择、权限、节点、工具、知识、生成、交付七类。
6. **发布策略**：社区版先显示风险；企业版可配置发布门禁和审批人。

第一版不要建设通用评测平台。只支持工作流 Skill 的 20 条用例、串行运行、结构断言和人工确认，先让合同审核或制度报告 Skill 跑通。

### 9.4 第二优先级：Skill 运行分析

当前 `token_usage_logs` 记录请求、模型、Token、状态和 Trace，但没有稳定的 Skill ID、版本与节点结果；管理端只能看整体调用，不能经营 Skill。

需要新增一份独立、追加写入的 Skill 运行事实：

```text
skill_run
  run_id / session_id / tenant_id / user_id
  skill_id / skill_version / selection_mode
  status / started_at / ended_at
  total_tokens / cost / artifact_count
  failure_stage / failure_code

skill_node_run
  run_id / node_id / node_type / sequence
  status / duration_ms
  tool_ref / approval_result / artifact_refs
```

管理端第一版只做四个视图：Skill 排行、版本对比、失败节点排行、单次运行详情。失败记录可转成验证用例。不要把这些字段继续塞进 Token 用量服务；新增 `skill_observability` 服务和独立集合，前端新增独立页面。

### 9.5 第三优先级：依赖健康与变更影响

工作流 Skill 已能引用写作规范、Tool/MCP 和脚本插件，运行时也会做权限检查。企业部署还需要在故障发生前知道依赖是否可用：

- Skill 详情显示依赖项、当前健康状态和最后检查时间；
- Tool/MCP、写作规范或权限变更前列出受影响的 Skill 和发布版本；
- 依赖失效时通知负责人，并允许运行一组冒烟用例；
- 发布时冻结依赖引用或明确采用“跟随最新版”，避免无感漂移；
- 模型只声明所需能力，例如视觉和上下文长度，默认继续由组织策略路由。

这项排在验证台和运行分析之后，因为它需要复用二者的用例与运行事实。

### 9.6 第四优先级：组织级发布治理（企业版）

现有发布、分享、安装和更新已经解决分发；企业版应在其上补治理：

- 草稿 → 待验证 → 待审批 → 已发布 → 已停用；
- 作者、验证人和发布审批人可分离；
- 按部门/岗位灰度，支持回滚到上一发布版本；
- 发布记录关联验证报告、依赖快照和变更说明；
- 审计谁批准、谁安装、谁使用以及权限拒绝原因。

只有客户明确需要时再做 SSO、组织同步、预算和数据保留等通用企业能力。社区版保留直接发布，不被企业流程拖慢。

### 9.7 把标杆场景做成“官方 Skill + 验证集”

现有专家包和外部 Skill 安装已经能承载复杂能力。推广所需的场景包无需新增产品实体，仓库或独立目录发布：

- Skill/专家包；
- 公开样例材料；
- 20 条验证用例和期望结果；
- 所需 Tool/MCP 清单及最小权限；
- 3 分钟演示脚本、安装说明和已知限制。

第一套建议选“企业制度资料 → 有引用的问答与报告”，因为不依赖客户业务系统；第二套再从真实咨询中选合同审核或跨系统浏览器任务。外部公众号使用同一验证集测评，自有视频号展示完整场景。

### 9.8 DSH `0.1.7` 如何进入路线

截至 2026-09-23，上游最新是预发布版 `0.1.7-alpha.2`。对 MOVO 有直接价值的是 Session V4、后台任务完成后的继续唤醒、服务重启后的 Web 重连、大工具结果与 MCP 图片保留、二进制文件传输和 `readBytes`。这些先作为 Runtime 稳定性升级，不包装成新的 MOVO 产品对象。

DSH 的插件管理、Agent 模式选择、Team 看板和语音界面暂不照搬。MOVO 已有自己的 Skill/Tool/MCP 管理，复制上游 UI 会产生两套入口。只有 Runtime 事件能稳定投影到现有 `execution-v3` 后，才增加缺失的后台任务状态。

### 9.9 接下来四个双周迭代

| 迭代 | 主交付 | 明确不做 | 验收 |
| --- | --- | --- | --- |
| 1 | DSH `0.1.7-alpha.2` 候选准入；确定 Skill Run 事件模型 | 新节点、智能体对象 | 旧会话、取消、后台任务、子代理、MCP 图片、文件交付全部回归 |
| 2 | Skill 验证台 MVP | 通用评测平台、复杂打分器 | 20 条用例可保存、运行、比较草稿与发布版并归因 |
| 3 | Skill 运行分析 MVP | 改造现有 Token 报表为巨型页面 | 可按 Skill/版本查看使用、完成率、成本和失败节点 |
| 4 | 依赖健康 + 企业发布审批原型 | 智能体市场、多渠道发布 | Tool/MCP 失效可定位受影响 Skill；一次审批、灰度和回滚跑通 |

四个迭代后再根据真实数据决定下一项：若大量失败来自自动选择，增强 Skill 路由评测；若来自长任务中断，补后台任务视图；若客户要嵌入门户或企微/飞书，再做稳定 API 和渠道适配。当前没有数据支持提前建设这些分支。

### 9.10 何时再考虑“智能体”

只有至少两个客户反复要求以下能力，才建立智能体对象：长期隔离的身份和系统指令、固定且独立的模型/知识/工具边界、独立负责人和预算、独立 SLA/审计空间，或需要把独立助手嵌入外部渠道。否则继续用通用 Agent、Skill 和快捷入口表达场景。
